# Assumptions

The brief leaves some details open. Each decision below is deliberate, and each one is covered by a test.

## Money

| # | Question | Decision |
|---|---|---|
| 1 | How are amounts represented? | Decimal end to end. Stored as `NUMERIC(18,2)`, parsed into Python `Decimal`, and returned as a **string** with 2 decimals (`"150.00"`). A float is never used for money: `0.1 + 0.2` gives exactly `"0.30"`. |
| 2 | What precision is accepted? | At most 2 decimal places. `10`, `10.5`, `"10.50"` and `0.1` are accepted. `10.001` is rejected (400 `INVALID_AMOUNT`). The value can be sent as a JSON number or a numeric string. |
| 3 | Limits | Each transaction must be `> 0` and `<= 1,000,000,000.00`. `NaN`, `Infinity`, booleans and non-numeric strings are rejected. A balance can hold up to 16 integer digits (`NUMERIC(18,2)`). A credit that would go past that limit is rejected with 422 `BALANCE_LIMIT_EXCEEDED`, and nothing is written. |
| 4 | Currency | There is a single implicit currency, so there is no currency field. |

## Accounts

| # | Question | Decision |
|---|---|---|
| 5 | ID format | UUID v4 generated by Postgres (`gen_random_uuid()`). Sequential integers were avoided because they reveal how many accounts exist and let anyone enumerate them. |
| 6 | What if the client sends `balance` (or `id`, `created_at`, any unknown field)? | **Rejected with 400 `VALIDATION_ERROR`**. The field is not silently ignored. The brief says the client "must not be allowed" to set the balance, and an explicit rejection makes that visible to the client. |
| 7 | Name rules | Leading and trailing whitespace is trimmed. After trimming the name must be 1–100 characters. Duplicate names are allowed, because names are not identities. |
| 8 | Is there an API to update or delete accounts? | No. The brief doesn't ask for one. At the database level, an account that has transactions cannot be deleted (`ON DELETE RESTRICT`). |

## Transactions

| # | Question | Decision |
|---|---|---|
| 9 | Endpoint shape | Nested: `POST /accounts/{account_id}/transactions`. The account comes from the path, and `account_id` appears in every response. |
| 10 | `description` | Optional, at most 255 characters, `null` when omitted. |
| 11 | `reference_id` format | Required string of 1–64 characters that must not be blank. It is compared **exactly**: case-sensitive and not trimmed, because it is an idempotency key. |
| 12 | **Response to a duplicate `reference_id`** | **409 Conflict**, code `DUPLICATE_TRANSACTION`. `details.existing_transaction` contains the original transaction, so a client that retried after a timeout still learns the outcome. No row is created and the balance doesn't change. |
| 13 | Duplicate `reference_id` with a *different* payload (e.g. a different amount) | Also 409, with the original returned unchanged. The first write wins. |
| 14 | **Which check runs first, duplicate or insufficient balance?** | **The duplicate check.** Example: a debit of 80 succeeded and the balance is now 20. If the client retries the same debit, the answer must be "already exists", not "insufficient balance". |
| 15 | **Are rejected transactions stored?** | No. The `transactions` table holds only valid, applied transactions, so `balance == SUM(credits) − SUM(debits)` always holds. A consequence: the `reference_id` of a rejected debit is still free, so the client can retry it after topping up. In production, rejected attempts would go to a separate audit log (see DECISIONS.md, *Next steps*). |
| 16 | Status code for insufficient balance | 422 Unprocessable Entity, code `INSUFFICIENT_BALANCE`. The request is well-formed but breaks a business rule. `details` contains the available balance and the requested amount. |
| 17 | Debit of exactly the balance | Allowed. The balance becomes `0.00`. |
| 18 | `type` | Exactly `credit` or `debit`, lowercase. `CREDIT` is rejected. |
| 19 | Response to a successful create | 201 with the transaction and the account's new balance, so the client doesn't need a second call. |

## History

| # | Question | Decision |
|---|---|---|
| 20 | Pagination defaults and limits | `page` defaults to 1 and `limit` to 20. `limit` can be at most 100 and `page` at most 1,000,000. |
| 21 | Invalid pagination values | A non-integer, a value below 1, or a value above the maximum returns **400 `INVALID_PAGINATION`**. Out-of-range values are rejected, not clamped, because the brief lists invalid pagination as an error case. |
| 22 | A page past the end | 200 with `data: []` and correct metadata. Not an error. |
| 23 | No transactions | `total_records: 0`, `total_pages: 0`. |
| 24 | Ordering ties | `ORDER BY created_at DESC, seq DESC`. `seq` is an internal, ever-increasing column that is never exposed. It gives a stable order when two rows share a timestamp, so rows don't repeat or go missing across pages. |
| 25 | Invalid `type` filter | 400 `INVALID_TRANSACTION_TYPE`. |
| 26 | Timestamps | `TIMESTAMPTZ`, returned as ISO-8601 in UTC (`2026-10-29T10:15:30.123456Z`). |

## Transfers (bonus)

| # | Question | Decision |
|---|---|---|
| 27 | Shape | `POST /transfers` with `from_account_id`, `to_account_id`, `amount`, `reference_id` and an optional `description`. |
| 28 | How is a transfer recorded? | As two ordinary transactions: a debit on the source and a credit on the destination. They share a generated `transfer_id`, and both carry the client's `reference_id`. Both legs show up in each account's history. |
| 29 | Transfer idempotency | The `reference_id` must be unused on **both** accounts. Otherwise the response is 409 and nothing changes. Replaying the same transfer is therefore safe. |
| 30 | Self-transfer | Rejected with 400 `SAME_ACCOUNT_TRANSFER`. |
| 31 | Default description | `"Transfer to <id>"` and `"Transfer from <id>"` unless the client provides one. |

## Errors

| # | Question | Decision |
|---|---|---|
| 32 | Error shape | Always `{"error": {"code", "message", "details", "request_id"}}`. This also applies to unknown routes (404), wrong methods (405) and unexpected failures (500). |
| 33 | Malformed vs non-existent IDs | An ID that isn't a valid UUID returns 400 `VALIDATION_ERROR`. A valid UUID with no matching account returns 404 `ACCOUNT_NOT_FOUND`. |
| 34 | Several validation problems in one request | `details` lists all of them. The `code` is specific (for example `INVALID_AMOUNT`) only when every problem is of that one kind. Otherwise it is `VALIDATION_ERROR`. |
| 35 | Out of scope | Authentication and authorization, rate limiting, multi-currency, and listing accounts. None of these are in the brief. |
